# 同步传输与信任模型（讨论稿）

> 状态：**讨论稿 v0.1**（2026-10-31）。`sync.sync-design` 的产物，供人评审后再开实现线。
> 本文只回答「怎么传、谁信谁」；不写实现细节，实现留给 `sync-kernel` / `sync-ui`。

## 1. 现状：内核已经能做什么

内核（hydrogen `5f3e8e3`，`shio 0.2.0`）把同步做成了**传输无关的帧**，应用侧只要当字节管道：

| 能力 | 符号 | 产物 |
|---|---|---|
| 导出变更 | `shio_sync_changes(after, limit)` | `SHY2` 帧 + 下一页游标 |
| 应用变更 | `shio_sync_apply(frame)` | 应用报告 JSON |
| 快照 | `shio_sync_snapshot_start` / `shio_sync_snapshot_page` / `shio_sync_apply_snapshot` | 分页 `SHY2` 帧 |
| 密钥轮换 | `shio_sync_offers` / `apply_offers` / `begin_rotation` / `rotation_state` / `ack_rotation` / `retire` / `prune_offers` | offer 帧 + 状态 JSON |
| 迁移 | `shio_sync_migrate_all` / `migrate_all_ex` / `migration_progress` / `cancel_migration` | 进度 JSON |
| 压缩 | `shio_sync_compact(before)` | 删除条数 |
| 配对 | `shio_sync_create_pairing` | `SHW2` 外层帧 + `{"secret":"<Base32>","fingerprint":"…"}` |
| 配对建库 | `shio_open_with_pairing(path, password, options, frame, secret)` | 新库句柄 |

**关键结论：内核不负责网络。** 帧是自包含的二进制块，端到端机密性与完整性由内核的密钥体系保证，
所以传输层可以选择「很笨」的通道（TCP、HTTP 上传下载，甚至文件），安全性不因此下降。

现有同步身份：每个库首次建库即 `sync_enable` → `format=2`（不可回退），库里有 `db_id` 与设备 ID；
`sync_info` 可读出摘要。也就是说**同步身份已经存在，缺的只是通道与 UI**。

## 2. 约束

| 约束 | 来源 | 对传输层的影响 |
|---|---|---|
| 当前 APK **不申请 INTERNET 权限** | `AndroidManifest.xml`、`docs/privacy` 定位（纯本地） | 任何网络方案都要**新增网络权限**，必须由人重新拍板隐私定位 |
| 库是 `format=2`，配对后新建库 | SPEC「内核 ABI 对齐」 | 同步以「本机库 + 另一台设备的配对包」为核心，不是账号体系 |
| 内核调用是阻塞的，JNI 串行 | SPEC「技术栈」 | 传输必须放在 IO 线程，且不能并发打多条 `apply` |
| 端到端加密由内核负责 | 上文第 1 节 | 传输层无需实现应用层加密，TLS 只保护元数据（帧大小/时序/IP） |
| 手机为主，可能无外网、无公网 IP | 使用场景 | 局域网直连对「同一 Wi-Fi 下两台手机」最省事 |
| 无后台常驻意愿 | 现有架构（无 Service） | 后台拉取要么走 WorkManager 周期任务，要么纯手动 |

## 3. 候选方案

### A. 局域网直连（设备对设备）

- 一台设备开监听（随机高端口，或 `NsdManager` mDNS 广播服务名），另一台用配对包里带的地址/发现结果连上去。
- 通道只需两条 RPC：`pull(after) -> frames` 与 `push(frames) -> report`。
- 首次配对靠二维码/短码搬运 `SHW2` 帧 + secret，**不走网络**。
- 优点：不依赖公网与服务器；延迟低；无第三方；隐私定位不变（只在内网）。
- 缺点：两端必须同时在线且同一网段；mDNS 在部分路由器/企业网被禁；IPv6/双栈要处理；仍需 INTERNET 权限（局域网 socket 也要）。

### B. 自建服务（用户自己的服务器 / NAS）

- 一个极简「帧信箱」：`PUT /frames`、`GET /frames?after=`，服务端只看得到不透明帧。
- 客户端配一个 base URL + 一次性令牌，走 HTTPS。
- 优点：不同网段/跨地域可用；离线也能排队；与内核的「变更日志 + 游标」模型天然契合。
- 缺点：用户要自备服务器（违背「开箱即用」）；服务端仍要知道谁是谁（令牌/设备注册）；TLS 与部署责任落在用户。
- 若要托管版，就变成「我们运营一个只存密文的信箱」——超出当前项目定位，需明确否决或单独立项。

### C. 云中继（第三方托管）——建议直接排除

- 与「纯本地、无账号、不上传」的既有定位冲突，且引入运营成本与合规义务。**建议在评审时明确写进否决项**，避免以后反复讨论。

### D. 文件式兜底（手工搬运）

- 复用已有序幕：导出变更帧到文件（SAF），另一台导入。
- 优点：零网络权限、零新基础设施；30 行代码级成本；对「偶尔同步一次」的用户够用。
- 缺点：需要用户手动搬文件；冲突与游标管理靠用户记忆。
- 定位：**兜底方案**，也是 A/B 都不可用时的最小可用形态。

## 3.5 对比

| 维度 | A 局域网直连 | B 自建服务 | C 云中继 | D 文件式兜底 |
|---|---|---|---|---|
| 新增网络权限 | 需要（`INTERNET`，局域网 socket 也要） | 需要 | 需要 | **不需要** |
| 外部基础设施 | 无 | 用户自己的服务器/NAS | 我们运营（最重） | 无 |
| 跨网段 / 跨地区 | ✗（同网段） | ✓ | ✓ | ✓（手动搬） |
| 两端同时在线 | 必须 | 不必（服务端排队） | 不必 | 不必 |
| 实现成本 | 中（发现 + socket + 错误重试） | 中高（客户端 + 服务端 + 部署文档） | 高 | 低（复用 SAF） |
| 与内核模型契合度 | 中（长连接一建立，游标很自然） | **高**（帧信箱 ↔ 变更日志 + 游标） | 高 | 低（一次一个文件） |
| 隐私面（元数据泄露） | 局域网内 IP / 帧大小 | 服务端知道设备与时间 | 第三方知道全部元数据 | 无（用户自己搬） |
| 维护成本 | 低（无常驻服务） | 中（服务可用性、证书、备份） | 高 | 最低 |
| 适合的用户 | 「两台手机在同一 Wi-Fi」 | 「有 NAS / 有云服务器」 | — | 「极少同步」 |

关键判断：三种网络方案**都要新增 `INTERNET` 权限**，而当前应用的卖点是「不申请任何网络权限」。
这是一次定位级的决策，不是实现细节 —— 因此本稿把它摆在问题 ①。

另一个关键点：既然帧由内核端到端加密，**A 与 B 的信任模型差异比想象中小**。
真正的成本差在「谁提供通道」：A 是两台设备自己，B 是用户自己的服务器，C 是第三方。

## 4. 推荐

**分两步，先窄后宽：**

1. **第一步（本次实现范围）：A 局域网直连 + D 文件式兜底**
   - A 覆盖真实主场景：同一个 Wi-Fi 下的手机 ↔ 平板 / 备用机。
   - D 覆盖「不在一张网」与「临时无网络」：导出变更帧到文件，另一台导入（复用已验收的 SAF 路径）。
   - 两者共用同一套内核帧与游标逻辑，D 相当于把「通道」换成文件，实现增量很小。
2. **第二步（可选扩展，不阻塞）：B 自建服务**
   - 只做「自定义 base URL + 令牌」的极简帧信箱客户端，**不提供托管服务**，不引入账号体系。
   - 什么时候做：当用户（我们）真的需要跨网同步时。
3. **C 云中继明确否决**，写进否决清单，避免反复摇摆。

配套约束（建议一并采纳）：

- **新增 `INTERNET` 权限要有文案说明**：设置页同步入口写明「仅用于与你自己配对的设备/服务器通信」，
  并在 `docs/vault.md` 的「安全与隐私」表里把「不申请网络权限」改成「不主动联网：只有你触发同步时才连局域网/自建服务器」。
- **不做后台自动拉取**（第一版）：同步由用户点击触发，避免 Service / WorkManager 与电量、被系统杀进程的问题。
- **第一版不接 `migrate*` / `compact` / `prune_offers`**：等真实数据量上来再谈，先把 changes/apply/snapshot + 配对 + 轮换跑通。

## 5. 待决问题（本次只定 ①，②–⑤ 分别留给 T2–T4）

1. **传输层**：A / B / D 选哪个？是否接受为局域网直连而新增 `INTERNET` 权限？
2. TLS 责任边界（T2）：A 方案下是否需要 TLS，还是「内核端到端加密已足够，明文 TCP 可接受」？
3. 配对密钥的展示/存储/撤销（T3）：二维码 vs 短码 vs 纯文本；secret 存哪里；撤销等于什么操作？
4. 冲突呈现与后台拉取策略（T4）：静默 LWW 还是逐条提示；是否允许 WorkManager 周期拉取。
5. 范围：`sync_offers`/`rotation`/`migrate`/`compact` 这些运维符号，第一版是否只做「轮换」而把迁移/压缩留到后面？
