# 同步传输与信任模型（讨论稿）

> 状态：**讨论稿 v0.1**（2026-10-31）。`sync.sync-design` 的产物，供人评审后再开实现线。
> 本文只回答「怎么传、谁信谁」；不写实现细节，实现留给 `sync-kernel` / `sync-ui`。

## 1. 现状：内核已经能做什么

内核（hydrogen `5f3e8e3`，`shio 0.2.0`）把同步做成了**传输无关的帧**，应用侧只要当字节管道：

| 能力 | 符号 | 产物 |
|---|---|---|
| 导出变更 | `shio_sync_changes(after, limit)` | `SHY2` 帧 + 下一页游标 |
| 应用变更 | `shio_sync_apply(frame)` | 应用报告 JSON |
| 快照 | `shio_sync_snapshot_start` / `shio_sync_snapshot_page` / `shio_sync_apply_snapshot` | 分页 `SHY2` 帧 |
| 密钥轮换 | `shio_sync_offers` / `apply_offers` / `begin_rotation` / `rotation_state` / `ack_rotation` / `retire` / `prune_offers` | offer 帧 + 状态 JSON |
| 迁移 | `shio_sync_migrate_all` / `migrate_all_ex` / `migration_progress` / `cancel_migration` | 进度 JSON |
| 压缩 | `shio_sync_compact(before)` | 删除条数 |
| 配对 | `shio_sync_create_pairing` | `SHW2` 外层帧 + `{"secret":"<Base32>","fingerprint":"…"}` |
| 配对建库 | `shio_open_with_pairing(path, password, options, frame, secret)` | 新库句柄 |

**关键结论：内核不负责网络。** 帧是自包含的二进制块，端到端机密性与完整性由内核的密钥体系保证，
所以传输层可以选择「很笨」的通道（TCP、HTTP 上传下载，甚至文件），安全性不因此下降。

现有同步身份：每个库首次建库即 `sync_enable` → `format=2`（不可回退），库里有 `db_id` 与设备 ID；
`sync_info` 可读出摘要。也就是说**同步身份已经存在，缺的只是通道与 UI**。

## 2. 约束

| 约束 | 来源 | 对传输层的影响 |
|---|---|---|
| 当前 APK **不申请 INTERNET 权限** | `AndroidManifest.xml`、`docs/privacy` 定位（纯本地） | 任何网络方案都要**新增网络权限**，必须由人重新拍板隐私定位 |
| 库是 `format=2`，配对后新建库 | SPEC「内核 ABI 对齐」 | 同步以「本机库 + 另一台设备的配对包」为核心，不是账号体系 |
| 内核调用是阻塞的，JNI 串行 | SPEC「技术栈」 | 传输必须放在 IO 线程，且不能并发打多条 `apply` |
| 端到端加密由内核负责 | 上文第 1 节 | 传输层无需实现应用层加密，TLS 只保护元数据（帧大小/时序/IP） |
| 手机为主，可能无外网、无公网 IP | 使用场景 | 局域网直连对「同一 Wi-Fi 下两台手机」最省事 |
| 无后台常驻意愿 | 现有架构（无 Service） | 后台拉取要么走 WorkManager 周期任务，要么纯手动 |

## 3. 候选方案

### A. 局域网直连（设备对设备）

- 一台设备开监听（随机高端口，或 `NsdManager` mDNS 广播服务名），另一台用配对包里带的地址/发现结果连上去。
- 通道只需两条 RPC：`pull(after) -> frames` 与 `push(frames) -> report`。
- 首次配对靠二维码/短码搬运 `SHW2` 帧 + secret，**不走网络**。
- 优点：不依赖公网与服务器；延迟低；无第三方；隐私定位不变（只在内网）。
- 缺点：两端必须同时在线且同一网段；mDNS 在部分路由器/企业网被禁；IPv6/双栈要处理；仍需 INTERNET 权限（局域网 socket 也要）。

### B. 自建服务（用户自己的服务器 / NAS）

- 一个极简「帧信箱」：`PUT /frames`、`GET /frames?after=`，服务端只看得到不透明帧。
- 客户端配一个 base URL + 一次性令牌，走 HTTPS。
- 优点：不同网段/跨地域可用；离线也能排队；与内核的「变更日志 + 游标」模型天然契合。
- 缺点：用户要自备服务器（违背「开箱即用」）；服务端仍要知道谁是谁（令牌/设备注册）；TLS 与部署责任落在用户。
- 若要托管版，就变成「我们运营一个只存密文的信箱」——超出当前项目定位，需明确否决或单独立项。

### C. 云中继（第三方托管）——建议直接排除

- 与「纯本地、无账号、不上传」的既有定位冲突，且引入运营成本与合规义务。**建议在评审时明确写进否决项**，避免以后反复讨论。

### D. 文件式兜底（手工搬运）

- 复用已有序幕：导出变更帧到文件（SAF），另一台导入。
- 优点：零网络权限、零新基础设施；30 行代码级成本；对「偶尔同步一次」的用户够用。
- 缺点：需要用户手动搬文件；冲突与游标管理靠用户记忆。
- 定位：**兜底方案**，也是 A/B 都不可用时的最小可用形态。

## 3.5 对比

| 维度 | A 局域网直连 | B 自建中继节点 | C 云中继（我们运营） | D 文件式兜底 |
|---|---|---|---|---|
| 新增网络权限 | 需要（`INTERNET`） | 需要 | 需要 | **不需要** |
| 外部基础设施 | 无 | **用户自己的服务器（已有）** | 我们运营（最重） | 无 |
| 跨网段 / 跨地区 | ✗（同网段） | ✓ | ✓ | ✓（手动搬） |
| 校园网 / 访客网可用 | ✗（客户端隔离，两端不可见） | ✓（只出不出入） | ✓ | ✓ |
| 两端同时在线 | 必须 | 不必（服务端排队） | 不必 | 不必 |
| 实现成本 | 中 + 被网络环境卡死 | 中（客户端）+ 中（服务端） | 高 | 低 |
| 与内核模型契合度 | 中 | **高**（帧信箱 ↔ 变更日志 + 游标） | 高 | 低 |
| 隐私面（元数据泄露） | 局域网内 IP | 服务端知道 db_id / 设备 / 时间 / 帧大小 | 第三方知道全部元数据 | 无 |
| 维护成本 | 低 | 中（服务可用性、证书、备份） | 高 | 最低 |

**决策（2026-10-31，human）**：选 **B —— 用已有服务器做传输中继**，需要开发一个中继节点。

理由：

- 实际环境是**校园网**：同一网络下终端互相不可见（客户端隔离），A 方案在现场直接不可用；
  跨网段/运营商场景（手机流量 ↔ 服务器）只有服务端方案能覆盖。
- 已有可用的服务器，B 的「外部基础设施」成本为零，只剩「多写一个服务端」。
- C 仍明确否决：不引入第三方，也不由本项目托管服务。
- D（文件式）**暂不入第一版**：有中继后它只是冗余兜底，留作将来「完全离线」场景。

代价（需要接受）：

1. 新增 `INTERNET` 权限，隐私表述从「不申请任何网络权限」改为「不主动联网：只有你触发同步时才连你的中继」；
2. 服务端会看到元数据（随机 `db_id`、设备标识、时间、帧大小），必须写进文档；
3. 多一份需要部署与维护的服务端代码（证书、备份、限流）。

## 4. 中继节点规格草案

实现栈与位置（2026-10-31 human 决定）：**Rust，放进 shio 内核仓库（hydrogen）**，与内核共用工具链；
本仓库（oxygen）只做客户端。

### 4.1 定位与职责边界

中继是**与业务无关的帧信箱**：只按 `(库, 设备)` 存取不透明二进制帧，不解析、不合并、不持有任何密钥。

非目标（写死，避免范围膨胀）：

- 不区分应用类型：密码库、笔记、待办……对中继来说都只是「某个库的帧」；
- 不做账号、不做多租户控制台、不做托管服务；
- 不做服务端搜索/去重/压缩/冲突合并（这些是内核的事）；
- 不做 HA 集群：单实例 + 备份，可丢数据（见 4.9 的恢复路径）。

### 4.2 概念模型

| 概念 | 说明 |
|---|---|
| 库（db） | 内核生成的随机 `db_id`（UUID 文本）。它是中继唯一的业务主键，跨应用通用 |
| 设备（device） | 内核的 device id（`sync_enable` 时确定）。中继按设备记录「已确认到哪」 |
| 帧（frame） | 内核产出的 `SHY2` / `SHW2` 二进制块；中继不理解内容 |
| 游标（seq） | **中继分配的每库单调递增序号（u64）**，与内核的 `after` 游标分离 |
| 令牌（token） | 设备级 bearer token，中继只存哈希 |

为什么游标由中继分配：内核的 `sync_changes(after)` 是**源库本地**的游标，跨设备没有可比性；
中继必须有自己的顺序，否则多设备并发推送时无法给接收端一个稳定的「我读到哪了」。

### 4.3 数据流

```
设备 A                     中继                       设备 B
  sync_changes(本地游标) → SHY2 帧
  POST /v1/frames  ──────▶ 追加 frames(db_id, seq=5,6)
                              ◀──────  GET /v1/frames?cursor=4   （设备 B 的 ack 游标）
  sync_apply(帧) 结果回报                                seq=5,6 帧
  POST /v1/ack {cursor:6} ─▶ 更新 devices(B).acked_cursor=6
```

- 推送方**不需要**先拉；接收方**不需要**在线——这正是服务端方案相对直连的价值。
- 「自己推的帧不要再拉回来」：`GET` 默认过滤掉**本设备**推送的帧（可选 `include_own=1` 供调试）。

### 4.4 API v1

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| `POST` | `/v1/frames` | Bearer | body = 一帧；头 `Idempotency-Key: <uuid>`；返回 `{"seq": N}` |
| `GET` | `/v1/frames?cursor=&limit=` | Bearer | 返回 `{"frames":[{"seq","blob_b64"}],"next_cursor","has_more"}`，`limit` 默认 20、上限 100 |
| `POST` | `/v1/ack` | Bearer | body `{"cursor":N}`；幂等（只前进不回退） |
| `GET` | `/v1/info` | Bearer | 本库积压帧数/字节、保留期、配额余量、`acked_cursor`、`truncated_from`、协议版本 |
| `POST` | `/v1/devices` | Bearer | 签发一次性入网码（供新设备配对），返回 `{"enroll_code","expires_at"}` |
| `POST` | `/v1/devices/enroll` | 入网码 | 用一次性码换该设备令牌 `{"token","db_id","device_id"}` |
| `POST` | `/v1/devices/revoke` | Bearer | 撤销某设备令牌 |
| `GET` | `/healthz` | 无 | 仅返回 `ok`，不泄露任何库信息 |

- body 为 `application/octet-stream`（帧）或小 JSON；**不做分页之外的查询**、不做批量删除。
- 协议版本前缀 `/v1`；响应头带 `X-Relay-Version`，客户端在同步页显示。

### 4.5 认证与入网（粒度待你确认）

- **设备级令牌**（不是库级）：`token → (db_id, device_id)`，可单独撤销一台设备而不影响其它设备。
- 服务端只存 SHA-256 哈希；客户端存 `EncryptedSharedPreferences`（Keystore 包裹）。
- 入网流程：老设备点「添加设备」→ `POST /v1/devices` 拿一次性码 → 与 `SHW2` 配对帧、`secret`、
  `base URL` 一起编码进二维码 → 新设备扫码 → `POST /v1/devices/enroll` 换自己的令牌。
- 首个令牌怎么来：中继命令行 `relay token issue --db <db_id>` 手工签发。
  （不让第一个设备走未认证注册，避免「谁先到谁占领 db_id」。）

### 4.6 保留、GC 与配额

- 帧按 `seq` 追加；`ack` 只记录每设备游标，**不立刻删帧**（其它设备可能还没读）。
- 删除条件（任一满足）：① 所有活跃设备 `acked_cursor >= seq`；② 超 `frame_ttl`（默认 30 天）；
  ③ 该库总字节超 `db_quota`（默认 100 MB）时从最旧开始淘汰。
- 淘汰后 `truncated_from` 前移；客户端发现 `truncated_from > 自己的 cursor` 就必须走**全量重同步**（4.9），
  而不是继续增量。
- 单帧上限默认 4 MB（`snapshot` 分页帧最大 1000 条，需内核侧确认上限，见开放问题 Q4）。

### 4.7 并发与顺序

- 同一 `db_id` 的写入串行化（sqlite 事务），保证 `seq` 严格递增；
- 幂等键 24 小时内去重，网络重试不会产生重复帧；
- 设备并发推送允许交错，中继只保证「每设备自身顺序 + 全局 seq 单调」，不保证跨设备因果序
  （因果由内核变更日志处理，跨设备乱序到达也安全）。

### 4.8 存储与部署

- 存储：**sqlite（WAL）单文件**。表：`frames(db_id, seq, blob, created_at, idem_key)`、
  `devices(db_id, device_id, token_hash, acked_cursor, created_at, last_seen)`、
  `db_state(db_id, next_seq, truncated_from, bytes, quota)`。
- 部署：单二进制 `relay serve --config relay.toml` + systemd；TLS 由前置（Caddy/nginx）或内置 rustls 终止。
- 运维：`relay token issue|revoke`、`relay gc --dry-run`、`relay stats`；备份就是拷 sqlite 文件（允许丢，见 4.9）。

### 4.9 失败与恢复

| 情形 | 处理 |
|---|---|
| 请求超时 / 5xx | 客户端按 `Idempotency-Key` 重试，指数退避，最多 N 次 |
| 令牌被撤销 / 换中继 | `401` → 同步页提示「需要重新配对」，不静默失败 |
| 帧被淘汰（`truncated_from > cursor`） | 客户端走 `sync_snapshot_start/page` 全量重同步，成功后重置 ack |
| 中继整库丢数据 | 同上：任一设备把当前状态作为快照重新发布，其余设备全量重同步 |
| 服务端磁盘满 | 先淘汰最旧帧，再到 `/v1/info` 报警；写请求返回 `507`，客户端提示 |

**关键取舍**：中继不是备份。帧是「传输中间态」，随时可丢；真正的副本在各设备的库文件里。

### 4.10 多应用（密码库 / 笔记 / 待办）如何共用

- 中继**只认 `db_id`**：每个应用的每个库都是独立 `db_id`，互不干扰；
- 令牌与配额都按库计；应用类型不进协议，避免「加一个应用就改服务端」；
- 将来若一个应用要同时同步多个库，客户端自己管多个 `db_id` 与多个令牌，中继无感；
- 运维统计可按 `db_id` 标签做（可选，不影响协议）。

## 5. TLS 与证书（草案，对应 T2）

### 5.1 威胁模型

| 对手位置 | 能做到什么 | 靠什么防 |
|---|---|---|
| 路径上的被动监听（校园网、运营商） | 看到目标域名、时间、帧大小、`db_id`、设备 id | **TLS**（内容本来就看不到，帧是密文） |
| 主动 MITM（伪造 Wi-Fi / DNS / 恶意代理） | 篡改或删除帧、注入垃圾帧、诱导客户端连假服务器 | **TLS 证书校验** + 内核帧自带认证 |
| 拿到服务器磁盘 / 备份 | 看到全部密文帧与元数据 | 无解（这就是信任边界）；因此服务端日志不落明文帧 |
| 拿到某个设备令牌 | 能读写该库的密文帧、能消耗配额 | 只能作恶到「垃圾帧」为止（内核会拒）；靠限流+配额+可撤销令牌止损 |
| 拿到服务器进程内存 | 看到密文帧 | 同上：中继从不持有密钥，解不开 |

关键点：**TLS 保护的是元数据与可用性，不是内容**。内容由内核端到端加密；但元数据（哪个库什么时候同步了多少）
在公网明文传输下就是泄露，而且没有 TLS 就无法保证帧没被中途删掉/换掉。

### 5.2 终止点在哪里

两个可选部署，二选一，**不提供明文监听**：

1. **前置反代（推荐）**：Caddy/nginx 终止 TLS，relay 只监听 `127.0.0.1:8080`。
   优点：ACME 自动续期成熟，日志/限流现成，relay 代码不用处理证书。
2. **内置 rustls**：证书路径进 `relay.toml`，手动/外部脚本续期。
   优点：单进程；缺点：证书轮换要重启或热加载。

两种都要求：拒绝 HTTP 明文（不 301 到 HTTPS，直接返回 400/444）；HSTS `max-age=15552000`。

### 5.3 客户端校验证书

- 用 Android 系统信任库（默认行为），**不做 SPKI pinning**。
  理由：个人域名 + Let's Encrypt，换域名/换 CA 就锁定用户，运维成本大于收益；内容已经端到端加密，pinning 增益有限。
- **不支持跳过校验**，也不提供「信任自签证书」开关；想用自签就得自己把 CA 装进系统。
- 同步页展示中继证书的**域名、指纹、到期日**，方便人工核对（发现异常可以手动停止同步）。
- 最低 TLS 1.2，优先 1.3；与服务端协商失败时保留错误码，不重试到死。

### 5.4 令牌与日志的传输卫生

- 令牌只放 `Authorization: Bearer`，**禁止放 URL 参数**（避免进服务端访问日志、Referer、崩溃上报）。
- 服务端日志：不记录 `Authorization`、不记录帧内容；IP 仅保留 7 天用于排查，之后每日清理。
- 客户端日志（如果有）：不记录令牌、不记录帧内容；错误只存错误码与 HTTP 状态。

### 5.5 密钥轮换与证书轮换

- 证书轮换（Let's Encrypt 90 天）：客户端无感，不需重新配对。
- **内核密钥轮换**（`sync_begin_rotation` 等）与传输层无关，第一版不接（见 Q8）。

| Q1 | 令牌粒度：**设备级**还是库级？ | **设备级**（可单独撤销），首个令牌由 `relay token issue` 命令行签发 | 设备级多一张表和一个入网接口；库级简单但「撤销一台就撤销全部」 |
| Q2 | 新设备入网方式 | 老设备 `POST /v1/devices` 拿一次性码 → 写进二维码 → 新设备 `enroll` 换令牌 | 二维码里多带一个码，扫描流程多一步 |
| Q3 | 游标赋值方 | **中继分配每库单调 `seq`**，与内核 `after` 分离 | 这是协议的地基；若你想让游标跟内核走，设计要重做 |
| Q4 | 单帧上限 | 默认 **4 MB**，需内核侧确认 `snapshot` 页（≤1000 条）会不会超 | 关系到服务端限流/配额与客户端分页策略 |
| Q5 | 丢帧恢复 | 发现 `truncated_from > cursor` → **snapshot 全量重同步**（不报错让用户手工收拾） | 决定第一版要不要现在就接 `snapshot_*` |
| Q6 | TLS 责任（T2） | 见 §5：公网必上 TLS（前置 Caddy 或内置 rustls）；客户端用系统信任库、弃 pinning、不提供跳过校验；禁明文 HTTP | 决定证书运维成本与换域名时的脆弱度 |
| Q7 | 冲突与后台（T4） | 第一版只展示内核 `apply` 报告统计；**不做**后台自动拉取，只在同步页手动触发 | 决定要不要引入 WorkManager |
| Q8 | 符号范围 | 第一版：`changes`/`apply`/`snapshot_*`/`create_pairing`/`open_with_pairing`/`sync_info`；`offers`/`rotation*` 第二版；`migrate*`/`compact`/`prune_offers`/`retire` 不接 | 决定 `sync-kernel` 的任务拆分 |

已确定、无需再问的：

- 中继不区分应用：**只认 `db_id`**，笔记/待办/密码库共用同一套协议与同一台中继；
- 中继不是备份：帧可丢，丢了走全量重同步；
- 单实例、无 HA、无账号体系、不托管。

## 7. 下一步

定了 Q1–Q8 后：T2（TLS）→ T3（配对与令牌）→ T4（冲突与后台）→ T5 定稿并逐条 `decision record`，
然后开两条新线：

- `sync-relay`（hydrogen 仓库里的 Rust 中继：API + sqlite + 命令行）；
- `sync-kernel`（本仓库：符号映射 + 客户端同步引擎）。
